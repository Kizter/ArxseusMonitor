# Audit aksesibilitas (WCAG 2.2 Level AA)

Dokumen ini mencatat hasil audit aksesibilitas jendela detail, tindakan yang
diambil, dan bukti pengukurannya. Audit dilakukan dua lapis: pembacaan statis
seluruh komponen React (struktur ARIA, nama aksesibel, urutan fokus) dan
pengukuran runtime lewat WebView2 DevTools Protocol (nilai `getComputedStyle`,
`document.activeElement`, kontras terhitung dari token CSS yang benar-benar
dipakai).

Lingkungan dan alat ukur sama dengan `docs/black-box.md` (Windows 11 build
26200, layar 2560×1440 @ 150%, jendela 360×520 CSS px).

## 2. Bukti ukur (CDP)

Diukur pada build release final (15 Nov, `target\release\hwmonitor.exe`, aset
ter-bundle), jendela 322×465 CSS px, skrip `bb-a11y.mjs` lewat WebView2 DevTools
Protocol.

### Struktur dan nama aksesibel

| Yang diukur | Hasil |
|---|---|
| Baris metrik (`button[aria-controls="why-panel"]`) | 5 baris |
| Sisa `aria-pressed` di dokumen | 0 |
| `aria-current="true"` | tepat 1 baris — baris terburuk (RAM saat itu), sesuai `worstMetric` |
| Nama aksesibel baris | `Beban CPU: 12,3%, 16 thread, Aman` — detail angka ikut terbaca |
| Detail terlihat vs nama aksesibel | cocok (`detailInName: true`) |
| Heading grup metrik | `Ringkasan metrik`, tersembunyi secara visual |
| Panel "Kenapa?" | `SECTION`, `aria-labelledby="why-heading"`, nama terhitung `Kenapa?` |
| Paragraf kosong | 0 |
| Landmark | `main` 1, `header` 1, `footer` 1 |
| Overflow horizontal | tidak ada (`scrollWidth = clientWidth`) |
| Ukuran teks terkecil | 14 px |

### Fokus dan keyboard

| Yang diukur | Hasil |
|---|---|
| Fokus ke `<h1>` setelah Tab | `document.activeElement` = `h1`, `:focus-visible` cocok, outline `solid rgb(88,166,255)` |
| Ring fokus baris metrik | `outline-offset: -2px` (CSS), induk `overflow: hidden` — ring digambar ke dalam, tidak terpotong |
| Gulir dengan tombol PageDown sungguhan | `scrollTop 0 → 396` dari maksimum 397, fokus tetap di baris CPU |
| Gulir dengan gesture roda tetikus (CDP) | `scrollTop 0 → 396,4` |
| Footer | menempel di dasar jendela (y 413–465 dari 465 px), tidak ikut tergulir |
| Pindah ke pengaturan | fokus pindah ke `<h1>` (`Pengaturan`), Tab berikutnya masuk formulir |
| Fokus setelah "Mengerti" | `document.activeElement` = `#status-banner`, `:focus-visible` cocok |
| Muncul dari tray saat fokus kosong | fokus jatuh ke `<h1>` (`HWMonitor`), `document.hasFocus() = true` |
| Muncul dari tray saat baris masih terfokus | fokus tetap di baris itu (tidak dirampas) |

Catatan alat ukur: PageDown yang dikirim lewat `Input.dispatchKeyEvent` **tidak**
menggulirkan apa pun (`scrollTop` tetap 0) karena aksi gulir keyboard dijalankan
di proses browser, bukan di renderer. Karena itu jalur ini diuji ulang dengan
tombol asli (`SendKeys` ke jendela yang difokuskan lewat `AttachThreadInput`,
dipastikan `GetForegroundWindow` = jendela aplikasi); hasilnya seperti tabel di
atas. Kesimpulannya: batasan alat ukur, bukan bug aplikasi.

### Catatan pelaporan WebView2

`getComputedStyle().outlineWidth` mengembalikan 1,78571 px untuk CSS 2 px.
Kontrol pembanding (elemen uji dengan `outline: 2px` dan `border: 2px`) juga
dilaporkan 1,78571 px, sedangkan `border: 4px` → 3,57143 px dan lebar kotak
40 px tetap 40 px. Jadi ini faktor pelaporan tetap (skala halaman 1,12) pada
panjang border/outline, bukan nilai CSS yang berbeda; garis fokus tetap 2 px CSS.

Temuan tambahan saat pengukuran: `document.visibilityState` tetap `"visible"`
meskipun jendela disembunyikan lewat `WM_CLOSE` (`IsWindowVisible=false`),
sedangkan `document.hasFocus()` berubah `true → false`. Penjaga fokus karena itu
memakai `hasFocus()` (F31).

## 3. Batas pengujian

- Pengukuran di atas memakai WebView2/Chromium; pembaca layar nyata (NVDA,
  Narrator) dan Windows Voice Access tidak tersedia di mesin uji, sehingga
  perilaku pengumuman (F25) dan mode kontras paksa (F28) dicatat sebagai
  prosedur manual untuk sesi uji responden.
- Uji text scaling 200% dan forced-colors mengubah setelan Windows; keduanya
  dicatat sebagai langkah manual, bukan bagian otomatis.
